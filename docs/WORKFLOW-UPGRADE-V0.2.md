# V0.2 设计草案：把常用法务工作做成预置动作

日期：2026-11-21。状态：设计与提示词草案，未接入界面、未调用模型、未进行本轮功能验收。

后续进展：本文保留最初设计时的状态。意见改写现已写入V0.2开发分支，尚未运行验证；其余动作仍为设计。最新范围见[意见改写实施记录](OPINION-REWRITE-V0.2.md)。

## 一句话结论

下一步在现有四入口内加入“合同首审、复核来稿、意见改写、准备审批材料”四个动作，自动带入本次所需的合同版本、历史问题与依据；用经确认的审查标准指导产出，再由法务采纳。

## 1. 成熟做法及本项目的取舍

下表的产品事实来自官方文档；“本项目设计”是据此作出的产品判断，不代表厂商已验证中国大陆私募投资场景或允许直接嵌入其服务。

| 已产品化的机制 | 官方资料 | 本项目设计 |
| --- | --- | --- |
| 引导式工作流：固定输入、参考资料、步骤和产物 | Harvey Agent Builder（原Workflow Builder）说明可将组织知识、先例、条件分支做成可复用工作流 [S1] | 用户选择工作动作，通常只补1–3项；后台自动组织所需资料，不要求她记提示词 |
| 审查标准包含首选文本、退让、内部说明、评论和审批角色 | Spellbook Customize Playbooks [S2] | 建“审查标准卡”；法律、公司要求、项目商业条件与历史先例分别标注；未获公司确认的卡只作示例 |
| 首审与对方修改复核分开，未覆盖变化单列 | Spellbook Redline Review明确全文和修订范围不同，未命中规则的修订仍需人工处理 [S3] | V0.2基于当前已有文本diff做来稿复核，同时保留历史未结事项和相关条款检查；不宣称已实现Word原生修订 |
| 条款例外有明确理由和审批角色 | Ironclad Playbooks允许请求非标准条款例外并跟踪批准 [S4] | 准备具体审批材料，区分谈判稿放行、风险例外、签署准备、投资审批法务材料；不自动作决定 |
| 将已有模板、审查指南和修改经验整理为规则 | LegalOn Playbooks官方说明支持组织首选立场、退让和风险容忍，并从已有材料归纳 [S5] | 从少量经确认的条款与标准开始；某次接受的让步不能自动变成通用底线 |
| 工作动作贴近Word | LegalOn Word介绍在Word内审查、修改并调用条款与模板 [S6] | 先形成“选条款—改意见—复制建议—上传新版本”；Word插件作为后续候选，先不增加部署负担 |

这些资料证明设计机制存在，不构成本工作台提效比例、模型准确率、商业API可用性或采购建议。未使用厂商营销百分比作为效果证据。

## 2. 首批四个动作

| 动作 | 页面位置 | 法务需要补什么 | 自动带入 | 产物与确认 |
| --- | --- | --- | --- | --- |
| 合同首审 | 合同 | 首次确认我方角色、交易类型；本次重点可选 | 固定版本、正文与解析警告、项目事实、获准标准、可用法源及附件目录 | 事实卡、逐条问题草稿、待补资料；采纳后进入审核意见 |
| 复核对方来稿 | 合同 | 确认比较基准和最新稿；本轮谈判目标可选 | 两版diff、相关正文、全合同未结root、已批准口径 | 本轮新变化、旧问题进展、关联影响、未覆盖项；旧问题只给处理建议不自动关闭 |
| 意见改写 | 审核意见 | 选内部法务/业务沟通/对方批注；选简洁/温和/坚定 | 所选意见、原始与当前条款、依据、经确认立场 | 对应用途的文字草稿及意思变化说明；保存为意见修订，不覆盖原判断 |
| 准备审批材料 | 交付物 | 审批类型、本次请批事项；业务理由可选 | 当前版本、全部未决问题、标准偏离、材料缺口、已批准事项 | 一页摘要、需决策项和附件清单；保存内部草稿，审批决定另由授权人作出 |

其他六个动作先保留任务定义：材料缺口检查、条款修改建议、跨合同一致性核对、法源问题准备、出稿前检查、经验沉淀候选。完整定义见 `prompts/catalog.json`。

界面继续只有合同、审核意见、法源、交付物四入口。提示词版本和详细参数放在可展开的设置中；日常用业务按钮。选择动作后显示简短“本次使用的资料”：版本、依据、审查口径和缺项，避免拿错稿。

## 3. 提示词、项目事实和公司标准分别保存

提示词描述工作方法，可由我们预置；项目事实从合同抽取并由人确认；公司底线与审批职责必须有真实来源。

### 项目事实卡

建议保存我方主体及角色、交易类型与阶段、已确认商业条件、法域和判断时点。每个事实附来源文件/版本/位置及确认状态。首次确认后按需复用；材料发生变化时提示差异，不静默改写已经确认的事实。

### 审查标准卡

建议字段：适用合同/角色/法域，检查目标，首选方案，可接受替代及条件，需要升级的偏离，依据类别，参考措辞，批准角色，生效时间与版本。

示例主题“解除通知对象”：先核对通知应到达谁；首选向合同相对方约定地址送达；由管理人收件时需核验授权；未获证实的代理关系列待确认。这里的首选、退让和升级条件只是设计示例，不能冒称公司制度。样例卡见 `prompts/playbook-example.json`。

### 条款与意见库

每条记录适用范围、我方角色、法域、来源、确认人和状态。模型可提出“这条值得收藏”的候选，法务确认后才成为可复用标准。项目特定例外单独保留，不自动泛化。

## 4. “做审批”的产品边界

| 类型 | AI可准备什么 | 人负责什么 |
| --- | --- | --- |
| 谈判稿对外放行 | 本轮修改、遗留风险、拟发送的准确版本、用途 | 是否允许该文件用于本轮谈判；现有V0只有本机演示的文件放行 |
| 风险例外请示 | 偏离哪个标准、为何偏离、影响、替代及附带条件 | 谁有权接受该风险、批准范围及有效期 |
| 签署前准备 | 未决项、授权证明、批准附件、签署版一致性、先决条件 | 是否允许签署、签署主体和权限是否有效 |
| 投资审批法务材料 | 交易摘要、主要法律问题、条件与待决策项 | 投委会/公司投资决策；工作台不替代该流程 |

AI生成“建议批准/附条件/暂缓”的分析时，必须标为建议并写明前提。没有审批矩阵时，审批角色写“待确认”，不能虚构董事长、投委会或法务负责人的权限。不存在“一个批准按钮完成以上全部事项”。

## 5. 基于当前代码的最小接入设计

已有：`version_id + sha256`、两版diff、意见root与历史、合同未结汇总、法源快照、内部/对外交付、人工批准失效。

尚缺：项目立场和事实卡、审查标准库、通用任务记录、冻结的任务资料包、意见正文改写留痕、草稿采纳入口、真实模型适配。当前 `analyze()` 始终以最早版本为baseline，只支持演示规则；不能直接视为多轮来稿复核。当前意见PATCH只改状态/说明，不能承担意见内容修订。

建议最小新增：

1. 工作动作目录：读取 `prompts/catalog.json`，在现有页面显示对应按钮。
2. 固定本次资料：记录任务/提示词版本，明确合同两版角色，固定版本摘要、意见与法源快照、标准版本。资料在运行中变化时，结果仍指向旧快照并标待复核。
3. 统一草稿：按动作生成意见草稿、复核建议、改写草稿或内部摘要；无模型时只能准备资料包或演示，不伪装完成。
4. 人工采纳回写：新增意见、保留意见正文修订、生成内部交付物；不提供AI关闭意见/批准交付的调用能力。

建议任务状态：资料待补 → 可生成 → 草稿待确认 → 已采纳/已驳回；材料更新后加“需重新核对”。只把相关材料带入每个步骤，不把全部项目档案塞入每条提示词。

## 6. 迭代顺序

第一项：意见改写。范围最小，立刻可用于把一条法务意见转换成业务沟通文字或对方批注；先保留草稿和原文，不改变实质立场。与它一起建立四动作共用的资料选择和输出结构。

随后：首审与来稿复核接入项目事实/标准；审批摘要汇总已经形成的意见。材料体检可作为前置步骤，不需要第五入口。

Word插件、多Agent调度、全量知识库、自动送审或自动审批不纳入本轮。真实模型接入仍沿用已有数据授权边界；外部法律检索只接收去标识化问题，不能夹带合同全文或客户信息。
